# #26 구현 계획

상태: 제품 구현 진행 중 / 검증·병합·운영 반영 전. M3에서 #26을 먼저 수행하며 #164는 별도 합의 전까지 진행하지 않는다.
명세: `specs/ui-sidebar-information-architecture.md` (2026-09-07-r3).
기술스택·저장 구조·API·알고리즘·의사코드는 명세 §10–20이 권위다. 이 계획은 그 구현 순서만 정의한다.
Work: W-UI-SIDEBAR-INFORMATION-ARCHITECTURE.

## 현재 코드에서 확인한 출발점

- `components/layout/Sidebar.tsx`는 `SidebarProjectsSection`과 `SidebarChatsSection`을 따로 렌더링한다.
- `navigation-contract.ts`의 `NavigationView`에는 chats/projects만 있고 그룹·배치 계약은 없다.
- `AppNavigationStore.listNavigation()`는 기존 세션/프로젝트 목록을 조합한다. 이 경로를 확장한다.
- 이름 변경/보관/프로젝트 즐겨찾기/생성은 기존 API를 사용한다. 그룹·세션 소속 이동은 새 동작이 필요하다.
- `POST /sessions`는 생성 후 작업 폴더를 준비하고 실패 시 생성 롤백을 한다. 소속 이동도 이 바인딩 소유권을 재사용해야 한다.
- 기본 채널 ID `general`은 이미 존재한다. 새 일반 채널을 또 생성하지 않는다.
- `ComposerTextArea`는 textarea다. 목업의 인라인 참조는 아직 제품 편집기·메시지 계약과 연결되지 않았다.
- 제목 생성 후 세션을 갱신하는 `AppGeneratedSessionTitleStore`가 있다. 분류는 기존 생성 경로에 결합하되 독립 실패로 취급한다.
- 목업 스마트 그룹은 여행 키워드 예제다. 실제 의미 분류가 구현된 것으로 세지 않는다.

## 하나의 제품 호출 경로

```text
사이드바/컴포저 또는 명시적인 에이전트 도구
  → 기존 App API (웹 HTTP / Electron bridge)
  → App application operation
  → sessions 도메인의 정리 / 소속 이동 / 참조 기능
  → 기존 App DB·세션 바인딩·메시지 저장
  → 기존 navigation/live projection
  → 같은 세션 ID를 사용하는 실제 화면
```

UI의 트리 배열이나 모델의 분류 결과는 저장 권한자가 아니다.
표시 배치와 실행 바인딩을 구분하고, 기존 상태/진척도를 읽어 표시한다. 별도 상태 추정 루프를 만들지 않는다.
새 기능은 현재 sessions 도메인 안에 책임별로 추가한다. 프로토타입 store를 운영 저장소로 승격하지 않는다.

## 순서별 실행 단위

### P1. 실제 그룹 저장과 혼합 트리 — 첫 구현

기존 CHAT-GROUPS Task를 확장한다.

- DB 그룹/배치 저장, 루트·프로젝트 범위, 형제 순서를 추가한다.
- 기존 navigation API/bridge/프로젝션을 확장하고 승인 DS 사이드바로 실제 세션을 렌더링한다.
- 생성/이름 변경/그룹 해제/메뉴 이동/즐겨찾기를 실제 동작으로 연결한다.
- 초기 이관은 기존 ID·이력·프로젝트 바인딩·즐겨찾기를 보존한다.
- 검사: 실제 UI에서 그룹 생성→대화 이동→새로고침→그룹 해제. DB 재개방 후 결과/ID 동일 확인.
- 완료: 메모리 목업이 아니라 웹과 Electron에서 같은 그룹이 보인다.

### P2. 탐색·상태·메뉴·스크롤 완성

기존 STICKY-TREE / SEARCH-FILTERS / CONTEXT-MENU Tasks에 대응한다.

- 전체보기/최신/진행중, 소속·시간·상태·진척도, fixed/sticky, 더보기를 연결한다.
- 기존 검색에 그룹·위치를 추가한다. 검색을 닫으면 원래 탭/트리 맥락을 복원한다.
- 기존 이름 변경/보관/프로젝트 대시보드/자동화/설정 진입을 보존한다.
- 상태는 기존 활성 턴/Work projection 사용. 모르는 진척도를 임의 퍼센트로 만들지 않는다.
- 검사: 승인 모바일/데스크톱 화면 비교, 긴 목록 sticky, 실행↔결정대기, 메뉴·키보드·길게 누르기.

### P3. 드래그 정리와 세션끼리 그룹 만들기

CHAT-GROUPS의 상호작용 단위다.

- 앞/뒤/안쪽 목적지, 루트 이동, 세션끼리 그룹 생성과 이름/되돌리기를 저장 API에 연결한다.
- 행 인스턴스 단위 마커, 즐겨찾기 중복 마커 회귀, 순환과 프로젝트 범위 검증을 포함한다.
- 모바일에서는 이동 메뉴로 같은 결과를 제공한다. 목업에 없던 터치 드래그 엔진은 새로 만들지 않는다.
- 검사: 실제 drag→저장→재접속, 그룹 자식 보존, 중복 즐겨찾기의 단일 마커.

### P4. 일반↔프로젝트 세션 소속 이동

새 Task: T-UI-SIDEBAR-SESSION-RELOCATION.

- 목적지 확인 UI와 세션 소속 이동 application operation을 추가한다.
- 기존 workspace binding/provisioning 기능을 호출하고 소속·배치를 함께 확정한다.
- 실행 중 경계/실패 복원/기존 파일 위치·메시지 ID 보존을 검증한다.
- 검사: 일반→프로젝트→일반 이동 후 실제 다음 요청이 올바른 작업 환경을 사용. 준비 실패 시 원래 세션 유지.
- 명세 §15의 prepareWorkspaceForRelocation 및 binding identity CAS를 구현한다. 기존 provision은 새 세션 전용이라 그대로 호출하지 않는다.
- App/binding/canonical scope 저장 경계는 relocation record와 공통 context admission gate로 연결한다. 트리 parent만 바꿔 완료 처리하지 않는다.

### P5. 컴포저 인라인 세션 참조

새 Task: T-UI-SIDEBAR-INLINE-SESSION-REFERENCE.

- Lexical 0.50.0 plain-text/history 기반 편집기와 DS inline DecoratorNode를 사용한다. Butler ContentPart 문서가 초안/큐/canonical 메시지/투영의 권위다(명세 §16).
- 드롭/참조 메뉴 모두 같은 커서 삽입 동작을 사용한다.
- 기존 첨부/붙여넣기/한글 IME/줄바꿈/수락 UI/큐 초안 기능을 보존한다.
- 모델 컨텍스트에 참조를 전달하고 실제 원문 조회 경로와 연결한다.
- 검사: 문장 중간에 복수 참조 삽입→삭제/undo→전송→재열람→참조 원문 조회.

### P6. 일반 채널에서 주제·프로젝트 분리

새 Task: T-UI-SIDEBAR-TOPIC-BRANCH.

- 기존 general을 지속 기본 채널로 노출하고 기존 자동화 전달 대상은 유지한다.
- 답변 액션 및 내부 도구에서 같은 branch operation을 호출한다.
- 요약·출처·원문 링크를 새 세션에 전달한다. 기존 대화는 삭제/이동하지 않는다.
- 검사: 실제 답변에서 주제 분리, 자연어 요청으로 프로젝트 분리, 원문 복귀, 새 세션에서 문맥을 이해하는 모델 응답.

### P7. 빠른 스마트 그룹

새 Task: T-UI-SIDEBAR-SMART-GROUPS.

- 기본 on 환경설정, 첫 메시지 이후 제한된 분류, 같은 주제 두 세션 묶기/기존 그룹 편입을 연결한다.
- 명세의 작은 입력 예산과 일반 제공자 수명주기, 자동 정리 안내/되돌리기, 늦은 결과의 수동 편집 덮어쓰기 방지를 적용한다. 분류 전용 시간 제한은 없다.
- 모델 출력은 목적지 후보이며 적용은 P1 정리 operation만 수행한다.
- 검사: 실제 모델로 같은 주제/다른 주제/기존 그룹/옵션 off/느린 응답. 대화 시작이 분류를 기다리지 않는지 측정한다.
- 명세 §18의 문자 bigram 후보 top16+최근8, 2,048 추정 입력 토큰, 짧은 JSON 출력 지침을 구현한다. 같은 configured provider/model(Codex 구독 포함)을 사용하고 분류 전용 deadline/출력 토큰 강제 상한 없이 응답을 기다린다. 호출은 일반 대화 처리와 분리한다.
- 3초를 넘겨 응답한 요청도 정상 적용되는지, 대화 처리가 기다리지 않는지, 대기 중 수동 이동한 배치를 보존하는지 검증한다.
- 제목 생성 완료를 기다리지 않고 첫 메시지 저장 이후 별도로 실행한다. topic exact index와 적용 직전 node revision 검증을 쓴다.

### P8. 전체 경로 검증과 운영 반영

- 각 단계에 필요한 좁은 테스트와 리뷰를 실행한다. 최종에는 위 경로를 하나의 사용자 여정으로 확인한다.
- 웹 HTTP와 Electron bridge 양쪽에서 같은 상태 저장/읽기, 새로고침/재시작 유지 확인.
- 실제 모델을 쓰는 참조·주제 분리·스마트 그룹 E2E. 현재 구성된 모델을 사용하고 전역 기본 모델은 바꾸지 않는다.
- 데스크톱 및 모바일 320/390/430px, 라이트/다크, 포커스/길게 누르기/IME를 확인한다.
- 물리 iOS Safari가 없으면 Chromium 모바일 검증과 구분해서 잔여 검증으로 보고한다.
- 완료 단계별 커밋, 최종 명세 대비 리뷰 후 기존 변경을 보존하여 main 통합, UI·에이전트 빌드/운영 반영을 별도 결과로 기록한다.
- 현재 계획 작성은 병합/배포 완료를 의미하지 않는다. 실제 배포 전 활성 작업 확인 및 사용자 승인 범위를 확인한다.
- 실제 동작 확인 후만 Task/Work 및 #26을 닫는다.

## 계획 검토

- 기존 다섯 Task로는 세션 이동/참조/주제 분리/스마트 그룹이 누락된다. P4–P7을 신규 Task로 등록해야 한다.
- SEMANTIC-SESSION-ORGANIZATION의 산출물은 이 명세/계획/목업이다. 제품 기능 완료와 구분한다.
- P1부터 실제 화면→저장→재열람이 이어지는 작은 단위로 진행한다. 기반 구조만 만들고 끝나는 단계를 두지 않는다.
- 참조는 실행 권한을 주지 않고, 그룹은 프로젝트를 바꾸지 않고, 스마트 분류는 응답을 막지 않는다.
- 정리 전용 쓰기 API가 바인딩을 받지 않도록 구조적으로 분리해 불변성을 지킨다.
- 활성 작업 중 이동 거부와 늦은 분류 결과 충돌은 현재 실사용 경계다. 무관한 복구 프레임워크는 추가하지 않는다.
- 개발 도중 확인되는 바인딩/편집기 제약은 해당 Task의 명세에 먼저 반영하고 승인된 사용자 경험을 편의상 변경하지 않는다.
- 완벽한 동작을 미리 단정하지 않는다. 구조상의 소유권 보장과 실제 경로의 테스트 증거를 함께 보고한다.

## 이번 정리의 산출물

- 최신 합의 명세와 구현 세부 제안을 분리했다.
- 승인된 모바일/데스크톱 목업을 원장 references에 보존했다.
- P1–P8 구현 순서와 각 단계의 검증/완료 기준을 정했다.
- 제품 코드 P1–P7 경로 구현 및 검증 중이다. 병합·운영 반영·이슈 완료는 P8 검증 이후 수행한다.

## r2 설계 검토 — 구현자에게 남겼던 결정 제거

- 스택: 기존 React/Zustand/Bun SQLite/DS/native DnD 유지, inline 편집에만 Lexical 추가.
- 자료구조: parent adjacency+정수 position. 이동 시 두 부모만 재정렬; 전체 트리 재작성 안 함.
- 쓰기 계약: expectedRevision, 동일 transaction의 저장/이벤트, 서버 inverse undo.
- 프로젝션: normalized store+행별 selector, native nested sticky, 실제 Work 상태 사용.
- 이동: 기존 API의 부적합을 확인하고 실제 두 저장소 사이 단계/진입 배제/중단 복구를 정의.
- 참조: App ID와 canonical ID 분리, 전송·queue digest·canonical parts·재투영까지 명시.
- 스마트 그룹: 후보 생성/순위/토큰 포장/모델 출력/적용 조건/실패 동작을 모두 명시.
- 검토에서 찾은 race를 반영: 읽기 확인만으로 admission 금지 불가 → 동일 DB UNIQUE gate 획득;
  CAS 후 phase 저장 전 crash → binding operationId로 전진 복구;
  다른 사용자의 tree 변경 → 전체 snapshot rollback 대신 영향받은 행만 적용.
- 이는 문서 경로 검토 결과다. 실제 실행 테스트나 E2E를 통과했다는 주장이 아니다.
